# PawCare Flutter 项目开发计划

> 制定日期：2026-10-10  
> 适用仓库：`paw-care-app`  
> 当前基线：Flutter 初始化模板，尚未接入 PawCare 业务  
> 第一阶段目标：完成可演示、可测试的移动端 MVP 闭环

## 一、项目目标

PawCare Flutter 客户端负责把现有后端、Agent 和健康数据能力串成真实用户流程。第一版优先完成：

```text
注册/登录
   ↓
创建并选择宠物
   ↓
查看宠物首页
   ↓
发起 AI 会话
   ↓
查看 AI 生成的健康记录
```

MVP 的完成标准不是页面数量，而是用户能够从注册开始，独立走通一次完整的宠物健康管理流程。

当前仓库只包含 Flutter 默认计数器模板：

## 三、开发原则

### 3.1 先完成主链路

首个版本只优先建设以下五个业务域：

```text
auth / pets / home / conversations / health-records
```

体重图表、相册、消息推送和复杂个性化设置放在 MVP 完成后。

### 3.2 以服务端数据为事实来源

- 用户身份以 JWT 和服务端响应为准。
- 宠物、健康记录和会话数据以服务端为准。
- 客户端只持久化登录凭证、当前宠物 ID 和少量界面偏好。
- `petId`、`threadId` 等安全上下文遵循后端已有边界，不由聊天页面自行拼装。

### 3.3 功能模块独立

采用 feature-first 目录，让每个业务模块包含自己的数据、状态和界面代码，公共能力放入 `core` 与 `shared`。

```text
lib/
├── app/
│   ├── app.dart
│   ├── router.dart
│   └── bootstrap.dart
├── core/
│   ├── config/
│   ├── network/
│   ├── storage/
│   ├── error/
│   └── theme/
├── features/
│   ├── auth/
│   ├── pets/
│   ├── home/
│   ├── conversations/
│   ├── health_records/
│   ├── gallery/
│   └── settings/
├── shared/
│   ├── widgets/
│   └── models/
└── main.dart
```

每个 feature 按实际复杂度使用以下子目录，不强制为空模块创建文件：

```text
data/          API、DTO、Repository 实现
domain/        业务模型和 Repository 契约
presentation/  页面、组件和状态
```

## 四、建议技术方案

| 能力 | 方案 | 用途 |
|---|---|---|
| 状态管理 | Riverpod | 登录态、当前宠物、列表及异步状态 |
| 路由 | go_router | 登录拦截、ShellRoute、深层页面导航 |
| HTTP | Dio | Base URL、JWT 注入、超时、错误转换 |
| 安全存储 | flutter_secure_storage | Access Token 等敏感凭证 |
| 普通存储 | shared_preferences | 当前宠物 ID、首次启动标记、界面偏好 |
| JSON 模型 | json_serializable | 服务端 DTO 序列化与反序列化 |
| 不可变模型 | freezed | 仅用于状态复杂或联合类型较多的模块 |
| 图片选择 | image_picker | 后续宠物头像与相册导入 |
| 日志 | 自建轻量 AppLogger | 开发期请求与异常记录，生产环境隐藏敏感数据 |

依赖在对应阶段按需引入，不一次性安装所有后续功能包。

## 五、开发阶段

### Phase 0：工程基础

目标：让后续业务在统一、可维护的底座上开发。

工作内容：

1. 清理默认计数器代码和模板测试。
2. 建立 `app`、`core`、`features`、`shared` 目录。
3. 配置 `dev`、`staging`、`prod` 环境及 API Base URL。
4. 建立 Dio 客户端：JWT 注入、超时、响应解析和统一错误转换。
5. 建立安全 Token 存储。
6. 建立 Riverpod 根容器。
7. 建立 go_router 与登录态重定向框架。
8. 建立 PawCare 主题：暖橙 `#FF9E64`、薄荷绿 `#64D2AA`。
9. 建立通用加载、空状态、错误状态与重试组件。
10. 修改应用名称、Android applicationId 和 iOS Bundle ID。
11. 补充 README 中的本地运行和环境配置说明。

验收标准：

- 应用能按指定环境启动。
- 能请求一个无鉴权或测试接口并正确显示成功/失败状态。
- 未登录访问受保护页面时自动进入登录页。
- `flutter analyze` 和基础测试通过。

### Phase 1：用户认证

目标：完成注册、登录、自动登录与退出闭环。

工作内容：

1. 对齐后端注册、登录和当前用户接口契约。
2. 实现登录页和注册页。
3. 保存 Token，并在请求中自动附带用户 JWT。
4. 冷启动时恢复登录状态。
5. 处理 Token 无效或过期后的统一退出。
6. 实现退出登录并清理本地用户数据。
7. 对表单校验、重复提交和服务端错误提供明确反馈。

验收标准：

- 新用户可以注册并进入应用。
- 已有用户可以登录。
- 杀掉应用后重新打开仍能恢复有效登录态。
- 无效 Token 不会造成循环请求或停留在错误页面。

### Phase 2：宠物档案

目标：完成当前宠物上下文，为首页、AI 和健康模块提供数据入口。

工作内容：

1. 对齐宠物 CRUD 的请求和响应模型。
2. 实现宠物列表、创建、详情、编辑和删除。
3. 实现当前宠物选择与切换。
4. 将 `currentPetId` 持久化到普通本地存储。
5. 处理首次使用无宠物、删除当前宠物和仅有一只宠物的状态。
6. 预留宠物头像字段，MVP 可先使用本地占位图。

验收标准：

- 用户只能看到自己的宠物。
- 创建第一只宠物后自动成为当前宠物。
- 重启应用后能恢复当前宠物；宠物不存在时能安全回退。
- 创建、编辑和删除后的列表状态与服务端一致。

### Phase 3：首页与应用主框架

目标：建立五栏主导航和当前宠物概览。

底部导航：

```text
首页 / 健康 / AI / 相册 / 我的
```

工作内容：

1. 使用 ShellRoute 建立主导航框架。
2. 首页展示当前宠物卡片和切换入口。
3. 展示最近健康记录。
4. 提供“问 AI”“添加健康记录”等快捷入口。
5. 为尚未开发的相册模块提供明确占位状态。
6. 统一各主页面的刷新和错误恢复行为。

验收标准：

- 切换底部导航时页面状态符合预期。
- 切换当前宠物后，首页数据同步刷新。
- 无宠物、无记录、网络失败均有可操作的页面状态。

### Phase 4：AI 会话

目标：让用户可以围绕当前宠物发起并继续 AI 对话。

工作内容：

1. 对齐 Conversation 和 Message API 契约。
2. 实现会话列表、新建会话、会话详情和删除。
3. 实现聊天消息气泡、输入框、发送状态和失败重试。
4. 前端只提交 `conversationId` 与 `message`，宠物和线程上下文由服务端解析。
5. 支持历史消息加载。
6. 展示 API 返回的 `warnings` 和降级状态。
7. 先完成普通请求响应，再根据服务端能力加入流式输出。

验收标准：

- 用户能创建会话并发送消息。
- 重新进入会话后能看到完整历史。
- 重复点击不会重复发送消息。
- Agent 部分降级时仍能展示回答和可理解的提示。
- 切换宠物不会误用其他宠物的会话上下文。

### Phase 5：健康记录

目标：让用户能查看、筛选和维护宠物健康事实。

工作内容：

1. 对齐 HealthRecord CRUD 与历史查询契约。
2. 实现记录列表、类型筛选和日期范围筛选。
3. 实现创建、详情、编辑和删除。
4. 针对 symptom、vaccine、medicine、checkup、weight、diet 提供对应标签和表单提示。
5. 从 AI 回答返回健康页后刷新记录，验证 Agent 自动写入结果。
6. 对 metadata 采用兼容未知字段的解析方式。

验收标准：

- 用户可以维护手动健康记录。
- 用户在 AI 中陈述明确健康事实后，可在健康列表看到服务端生成的记录。
- 切换宠物、筛选和刷新不会混淆数据。

### Phase 6：MVP 联调与体验收口

目标：形成第一版可演示、可测试的端到端产品。

工作内容：

1. 对主链路进行真机端到端联调。
2. 统一加载、错误、空状态和离线提示。
3. 检查小屏设备、键盘遮挡、安全区和深色模式表现。
4. 清理日志中的 Token、用户隐私和健康信息。
5. 添加核心模型、Repository 和关键页面测试。
6. 完成 Android debug APK 与 iOS debug 构建验证。
7. 编写演示数据准备与验收清单。

验收场景：

```text
注册账号
→ 创建宠物“咪咪”
→ 在首页确认当前宠物
→ 创建 AI 会话
→ 发送“咪咪今天吐了两次”
→ 获得 AI 回复
→ 打开健康页面
→ 看到新建的 symptom 健康记录
```

## 七、接口对齐清单

每个业务模块开始编码前，需要从后端当前代码或 OpenAPI 文档确认：

| 项目 | 需要确认的内容 |
|---|---|
| Base URL | 本地开发、测试和生产地址 |
| 响应外壳 | 是否统一包含 `data`、`message`、`meta` |
| 错误格式 | 状态码、错误码、字段校验错误结构 |
| Auth | 注册、登录、Token 有效期、刷新机制、当前用户接口 |
| Pet | 字段、枚举、日期格式、头像上传方式 |
| Conversation | 创建参数、消息分页、删除语义、是否支持流式响应 |
| HealthRecord | recordType 枚举、metadata 结构、日期和时区规则 |
| Warning | `warnings` 与 `meta.degraded` 的准确返回位置 |

没有经过接口核对的字段不直接写死到正式模型中。

- HTTP 错误转换。
- Token 状态与登录状态恢复。
- 当前宠物选择和失效回退。

### Widget 测试

- 登录表单验证。
- 宠物为空时的引导。
- 聊天发送、失败和重试状态。
- 健康记录筛选状态。

### 集成测试

- 登录 → 创建宠物。
- 创建 AI 会话 → 发送消息 → 查看历史。
- AI 写入健康事实 → 健康列表出现记录。

每个阶段至少保持：

## 十、建议开发节奏

每个阶段按同一节奏推进：

1. 阅读并确认服务端实际接口。
2. 定义客户端模型和 Repository 契约。
3. 实现数据层与状态层。
4. 实现页面和交互。
5. 覆盖关键失败状态。
6. 运行格式化、静态分析和必要测试。
7. 使用真机或模拟器完成阶段验收。

不以固定日期承诺阶段完成时间。每个里程碑验收通过后，再进入下一阶段，避免多个未完成模块同时堆积。

## 十一、主要风险

| 风险 | 影响 | 应对方式 |
|---|---|---|
| 后端契约与阶段总结不一致 | 客户端模型返工 | 每个模块开始前检查后端当前代码或 OpenAPI |
| Token 暂无刷新机制 | 登录体验不稳定 | Phase 1 明确过期策略并统一处理 401 |
| AI 响应耗时较长 | 用户误以为卡死、重复发送 | 明确发送状态、禁止重复提交、支持失败恢复 |
| 流式协议尚未确定 | 聊天层重复实现 | MVP 先完成普通响应，确认协议后抽象流式传输 |
| HealthRecord metadata 灵活 | 解析失败 | 保留原始 Map，并只读取已知字段 |
| 当前宠物状态跨模块共享 | 数据串宠 | 统一由单一 Provider 管理，切换后使相关查询失效 |
| 图片能力过早引入 | 拖慢主链路 | 头像先用占位图，相册放到 MVP 后 |
